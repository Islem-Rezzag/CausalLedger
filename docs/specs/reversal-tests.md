# M04.17 Reversal tests

This slice adds tests for the existing M04.09 full linked reversal contract. It changes no production API, source, permission, migration or financial authority. The original remains posted and immutable; its offset is a separate journal linked by an immutable reversal record. Synthetic consistency is software evidence and does not establish economic truth or human financial approval.

Inputs are synthetic posted journals, explicit Account snapshots and full inverse requests. Outputs are frozen pure identities or deterministic refusals, and stored receipts under the approved disposable PostgreSQL17 test route. Pure comparison checks the supplied original; stored existence, second reversal, reversal-of-reversal and ordinary08 adoption checks require database history.

For example, an original debits one asset by1000+250 and credits a distinct counteraccount by1000+250. Before reversal the accounts have1250 and-1250 debit-normal balances. A new linked journal credits the first account and debits the second by exactly1000+250, leaving both zero. A balanced partial750+250 offset is refused: balancing is insufficient when every original line must be reversed in full. No original header, line, snapshot or provenance reference is rewritten.

The corpus covers every ordered pair of the five account categories, USD/EUR/GBP, and four literal amount shapes:1250,1000+250, two signed64 maximum lines, and amounts beyond Number precision. The300 pair/currency/shape cases preserve exact normal-side signs and nonzero original balances before the offset; equal debit/credit totals and zero balances after it. Fifteen cases compose the existing cash/provider/customer/fee/revenue role helpers separately per currency. A general04 multicurrency journal covers all five categories with repeated maximum lines and aggregate totals beyond signed64. Role helpers remain single-currency. Account owners, provider identity and fee/revenue source contexts remain caller declarations.

Policy cases have independent literal pure paths and SQLSTATEs. Partial/future/unknown-field wrappers refuse at `$`/22023. Pending inverse/self-link refuse at `$.journal.transaction`/23514. Omitted event/receipt or changed receipt hash keeps valid nonempty provenance but fails retention at `$.journal.transaction.provenance`/23514. The fixture original and inverse data are detached so a mutation cannot change both sides of a comparison. Strict wrapper preflight and getter nonexecution are tested before any connection attempt.

All database cases compare full five-table histories as ordered SQL row text. One statement returns arrays of three strings per row: transaction ID, reversal original ID (empty for other tables), and the complete `to_jsonb(row)::text`. Primary-key ordering includes transaction/account and ledger/source/key components; money never passes through Number or a decoded aggregate. The after-offset snapshot supplies both exact authorized-ID exclusion views and the accepted history, avoiding duplicate global reads; a fresh post-retry snapshot still proves no mutation. Exact readback includes bigint amounts, totals, original posted status, snapshots and provenance. Only explicitly authorized new original/offset IDs are excluded when comparing prior history; new rows are inspected separately. Same-scope retries may change valid attempt IDs and declaration ordering but must return the first committed receipt without creating attempt rows, including on a fresh connection.
