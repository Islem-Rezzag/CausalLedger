# M04.09 Full linked reversals

`packages/ledger` owns `m04.09-ledger-reversal.v1`. The input is a strict record:

```json
{"contractVersion":"m04.09-ledger-reversal.v1","kind":"full","originalTransactionId":"txn_00000000000000000000000001","journal":{"contractVersion":"m04.04-ledger-journal.v1","transaction":{},"entries":[]}}
```

The abbreviated journal above shows shape only. A real candidate requires the complete unchanged M04.02 header/M04.03 lines and supplied valid Account catalog. `validateLedgerReversalCandidate(input, originalJournal, originalAccounts, suppliedAccounts)` checks supplied metadata and returns a frozen identity or deterministic issues. It cannot prove storage existence, provenance authenticity or reversal eligibility outside those supplied facts. `createLedgerReversalStore(explicitPostgresUrl)` exposes only `append(input, suppliedAccounts)` and `close()`. It is an infrastructure primitive, never an investigator or agent tool.

Only **one full reversal** of a stored original is supported. Both original and offset must have `posted` header metadata. Partial amounts, a second reversal under another key, missing originals, self-links and reversal-of-reversal are refused. No header lifecycle or general posting eligibility engine is introduced. The original header, accounts and entries remain byte-identical, including its `posted` status; a reversal is represented by the immutable linked offset. Posted metadata and balanced synthetic data do not establish authenticated financial truth or human repair approval.

Every original entry is copied with debit/credit swapped. Ledger, account, currency, positive minor-unit string, contract version and line multiplicity are conserved exactly. New transaction/entry IDs are required; no partial amounts, line split/merge, inferred accounts, currency netting or rounding. Referenced Account snapshots must match every original field, including lossless UTF16 name units, owner and status. The whole supplied catalog validates before filtering unused snapshots. Original event IDs and receipt/hash pairs must remain; additional explicit unique references are permitted. Conflicting or omitted original receipts refuse. The new header source identifies the reversal request; the original source remains accessible through the explicit original link.

The immutable `ledger_reversals` table stores original ID, unique reversal ID, ledger ID, version and full kind. Same-ledger composite foreign keys require both complete stored journals. The owner-only implementation of `append_ledger_reversal(jsonb,jsonb)` independently reconstructs and validates the stored original and performs exact inverse multiset/snapshot/provenance comparisons. Application roles have SELECT and narrow routine execution, no direct DML. PUBLIC execution is revoked; fixed search path and immutable UPDATE/DELETE/TRUNCATE triggers preserve history. Restricted separate identities are checked at migration entry. Administrators outside these role/trigger controls remain outside this guarantee.

The routine takes M04.08's exact `(ledgerId, source.namespace, idempotencyKey)` bigint advisory lock first, then the original's lock in PostgreSQL's disjoint two-int lock space. All09 calls use that order; READ COMMITTED and separate volatile commands obtain fresh snapshots after waits. Hash collisions serialize unrelated requests within either space; full keys and original IDs remain authoritative. The unchanged08 append and09 link insertion share one atomic statement. Failure rolls back all newly inserted journal, key and link records. Constraints and locks enforce one full reversal for this path.

Same original, wrapper version/kind, key scope and exact08 canonical journal identity return the committed09 receipt, including its original committed reversal ID. New valid attempt IDs and set/entry/catalog ordering can change. Both clocks, source, provenance, line multiplicity and referenced snapshots remain identity fields. Different payload, original or key refuses. A pre-existing ordinary08 outcome can never be adopted as a reversal, even when its inverse payload is identical. Legacy05/08 APIs remain available and cannot classify every economically inverse journal as a reversal; no economic exactly-once guarantee is claimed across alternate paths.

Storage errors expose only a sanitized SQLSTATE and `not_stored` or `unknown`. Recognized validation/constraint/permission/cancellation/serialization/deadlock failures confirm rollback. Lost acknowledgement or malformed receipt is unknown; no automatic retry occurs. Explicitly retry the same original, scope and semantic payload on a fresh connection to recover the linked result. Driver messages, SQL, credentials and hostile metadata accessors are not surfaced. Receipt data must be strict own enumerable data fields with the matching original, full kind, valid distinct committed ID and exact entry count.

The additive09 migration preserves05/08 DDL and performs no history backfill. Down refuses populated reversal history or wrong ownership. The owned synthetic Postgres17 runner requires empty **three-migration** UP/DOWN/UP, byte-identical populated05→08 and08→09 upgrades, exact six public tables/ten functions, all five sequential database suites and owned-resource cleanup. No user database is selected or reset.

Executable unit/type and mandatory real17 tests cover inverse amounts, currencies, distinct counter accounts, per-line maximum/unbounded aggregate totals, multiplicity, snapshot/provenance drift, renamed retry IDs, races, rollback, fresh connection recovery, ordinary08 adoption refusal, permissions and immutable constraints. The USD/EUR/GBP1250 demonstration stores a posted debit/credit journal and its full inverse, reads both account balances as zero at explicit effective/recorded cutoffs, and refuses partial/second reversals. No live money, raw evidence, repair approval or agent financial authority changes. M04.10 and later remain unstarted.
