# Provider clearing account — M04.11

The `m04.11-provider-clearing-account.v1` configuration is an explicit caller-supplied `{ contractVersion, role: "provider_clearing", provider: { namespace, id }, account }`. Provider clearing represents a temporary provider-side position awaiting settlement or reconciliation. This slice configures it as asset/debit-normal metadata over the unchanged M04.01 Account. It does not implement captured funds, refunds, fees, disputes, payouts or adjustments as workflows or universal accounting policy.

The provider reference uses the reviewed opaque reference syntax: namespace is a lowercase ASCII letter followed by up to 63 lowercase letters, digits, dots or hyphens; ID is 1–128 ASCII characters, starting alphanumeric and continuing alphanumeric, dot, underscore, colon or hyphen. Full-span matching rejects trailing newlines. References are exact and case-sensitive; no trimming, coercion, defaulting, generated ID or inference from Account name/owner or transaction source is permitted. Provider, Account owner and the originating source-record reference have distinct meanings and may differ.

`validateProviderClearingAccountCandidate(unknown)` requires strict own enumerable data records, validates the provider reference and delegates all Account fields to M04.01. Success returns detached frozen configuration/provider/Account data; failure returns deterministic issues without partial output. Closed metadata remains inspectable.

`validateProviderClearingJournalCandidate(journal, configuration, context)` requires strict `{ provider: { namespace, id }, accounts }` context. The supplied provider must match the configuration exactly. The captured complete catalog must contain the exact clearing Account snapshot, which must be active. The journal must use its configured ledger and currency on all lines, include the clearing account and a distinct counteraccount, and pass full M04.04 header, entry, ID, reference, provenance and exact bigint arithmetic validation using the detached catalog. Result is an ordinary frozen M04.04 journal, with no provider-registration, persistence, write, approval or posting method.

Provider isolation here means consistency between explicit configuration and context for one call. These caller assertions are not authenticated. The helper does not maintain a global or durable Account-to-provider mapping, require Account owner to be the provider, or equate a source event ID with a provider identity. The wrapper/context are not persisted in existing Account snapshots and existing storage/SQL do not universally enforce them. Durable ledger queries select accounts/currencies and explicit cutoffs; they do not query or prove provider classification.

The executable synthetic example debits provider clearing by 1250 and credits a separately supplied counteraccount. A later explicitly supplied opposite journal returns both arithmetic balances to zero. Another provider uses distinct accounts in the same ledger and its balance remains separate. Both inclusive query clocks apply. Zero does not prove a real capture, payout, bank posting, settlement, reconciliation, evidence authenticity or financial truth.

Unit/type tests and the mandatory seventh owned PostgreSQL17 composition suite cover exact context/snapshot matching, independent provider namespace/ID refusals, malformed references, currency/ledger/lifecycle/identity/provenance failures, large exact amounts, lossless names, immutable original readback and pre-I/O refusal. All six prior suites (215 real tests), all THREE byte-identical migrations, empty UP/DOWN/UP recovery, both populated upgrades, exact six public tables including `pgmigrations` and ten functions, and owned/Compose cleanup remain required. No new DDL, provider integration or event mapper is added. Agents receive no posting, money mutation, repair approval or evidence modification authority.

M04.12 customer liability and later account roles remain unimplemented.
