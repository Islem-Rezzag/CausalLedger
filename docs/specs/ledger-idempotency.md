# M04.08 scoped journal idempotency

`createIdempotentLedgerJournalStore(explicitPostgresUrl)` owns a private connection, exposes only `append(unknownJournal, unknownAccountCatalog)` and `close()`, and uses `m04.08-idempotency.v1` receipts. This is a deterministic synthetic storage boundary, not an agent tool or posting eligibility/repair approval. The prior M04.05 store and migration remain unchanged.

Scope is exactly `(transaction.ledgerId, transaction.provenance.source.namespace, transaction.idempotencyKey)`. All components are explicit validated values, compared case-sensitively with C collation. No default tenant, expiry, key reuse/deletion or lookup by key alone. IDs/reference labels do not authenticate callers or evidence.

The pure `validateLedgerIdempotencyCandidate` validates the complete journal and supplied catalog before returning frozen scope plus exact canonical JSON. Identity includes journal/header/entry versions, ledger, status, effectiveAt, recordedAt, complete source ID, moneyEvent/evidence sets, exact account/side/currency/integer minor units and every referenced Account snapshot field. Names are encoded as UTF16 code units without normalization. It excludes only attempted transaction ID, entry IDs, entry transactionId and the key already in scope. New valid attempted IDs can differ on an explicit retry; the original receipt always contains the original transaction ID. Both timestamps remain material, so generating a new recordedAt is a conflict.

MoneyEvent/evidence sets are sorted by identity, snapshots by account ID, and entries by semantic account/side/minor-unit-string/currency after removing attempt IDs. Object field and set/entry/catalog order do not matter. Duplicate semantic lines retain multiplicity. Splitting/merging balanced lines, changing evidence, status, clocks, referenced account metadata or amount conflicts. Only referenced accounts enter identity, after validating the entire supplied catalog. No decimal/float conversion, per-currency netting or inferred meaning.

Postgres independently validates wire input and derives the same JSONB semantic identity; it does not trust a caller hash. Exact JSONB equality avoids digest collision assumptions. Malformed IDs, duplicate attempted IDs, header refs, snapshots and amounts are refused even for a previously reserved key. Exact bounded line money and unbounded numeric per-currency equality remain mandatory.

The new volatile definer routine requires READ COMMITTED. It takes a transaction advisory lock derived from the full scope, then uses separate lookup/append/insert statements. A waiting caller receives a fresh snapshot after the lock. Hash lock collisions merely serialize unrelated keys; the C-collated triple primary key is durable authority. Header, all entries, referenced snapshots, canonical payload and original receipt commit in one autocommit statement. Same scope/same payload returns the persisted original receipt, including on a fresh connection. Different payload raises23505 with no writes. Failed validation, durable ID collision, key insertion failure or rollback leaves no partial journal or reservation. No mutable pending reservation or no-op UPDATE.

The explicit URL forbids ambient credentials/parameters. The private driver establishes READ COMMITTED before each routine call. Connection/setup failures are `not_stored`; recognized server refusals expose only sanitized SQLSTATE. Lost execution/commit acknowledgement and invalid response are `unknown`, with the connection discarded. There is no automatic retry; the caller can explicitly retry the original scope and semantic payload to recover its committed outcome. A retry must retain clocks/material payload. This does not guarantee economic exactly-once across different keys, namespaces or the legacy API.

Migration `1780000003000_m04_08_idempotency.cjs` adds the reservation table and two functions. Composite foreign key anchors original transaction/ledger. Restricted owner/app identities, fixed definer search path, revoked PUBLIC/helper execution and direct app DML, and immutable UPDATE/DELETE/TRUNCATE triggers protect history. App can read reservations and execute only the new append routine. The owner is a trusted migration identity; no production tenant authorization or general evidence authenticity is implemented.

No legacy backfill/adoption occurs: existing headers may share retry-key metadata and remain unreserved. Calling the new API with an existing legacy durable transaction ID refuses its duplicate; a new valid ID can start a new reservation, so callers must not treat legacy writes as covered by this contract. The legacy API still rejects identical durable IDs. Additive upgrade preserves populated legacy rows exactly. Empty full two-migration UP/DOWN/UP and populated05-to08 upgrade run in the owned runner;08 down refuses populated reservations, and05 down still refuses populated journals. No history is removed for recovery.

Executable demo: `ledger-idempotency.test.ts` exercises the driver boundary; `ledger-idempotency-postgres.test.ts` runs synthetic USD1250 debit/credit under key K, a renamed retry returning the original receipt, and USD1251 under K refusing without a second journal. Real acceptance also tests eight competing calls, observed two-connection waits for commit/conflict/rollback, insert-failure rollback, explicit fresh-connection recovery, scope isolation, semantic changes, malformed replay, permissions/immutability/FK/uniqueness and legacy behavior. Driver doubles are not database evidence. The existing runner requires owned Postgres17 and runs all four suites sequentially; configuration absence fails rather than skipping.
