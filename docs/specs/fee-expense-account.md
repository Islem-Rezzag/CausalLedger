# M04.13 Fee expense account

`packages/ledger` owns the pure `m04.13-fee-expense-account.v1` contract. Input is exactly `{contractVersion, role:"fee_expense", account}`. `validateFeeExpenseAccountCandidate(unknown)` delegates the unchanged M04.01 Account contract and requires explicit `expense`/`debit` metadata. Closed metadata remains inspectable; new fee journal examples require an active Account. IDs, owner, ledger, currency, amount and role are supplied without generation, inference, defaults or normalization. Fee expense covers explicitly identified provider, network, bank or operational fees; this validator does not calculate, recognize, collect or authenticate a fee.

`validateFeeExpenseJournalCandidate(journal, feeWrapper, context)` takes exactly `{source:{namespace,id}, accounts}`. The source uses M04.02's grammar: namespace is a lowercase ASCII letter plus at most63 lowercase letters/digits/dot/hyphen; ID is1–128 ASCII characters, first alphanumeric and then alphanumeric/dot/underscore/colon/hyphen. This13-owned check requires the entire string to match, including refusal of trailing line terminators. It captures strict own enumerable data once, accepts plain/null-prototype records, and refuses accessors, symbols, hidden/extra fields, class instances and inspection failures without leaking exceptions or calling getters.

The full supplied catalog is detached and validated once using unchanged01 validation. The configured fee Account must match every catalog snapshot field exactly, including lossless UTF16 name units. Complete04 journal validation uses that detached `catalog.value`; it checks the full header/entries and original evidence/event/duplicate/conflict/amount/reference rules. Then the checked header's `provenance.source` must equal the captured source namespace and ID exactly; every entry belongs to the configured ledger and single fee currency, with fee participation and a distinct counteraccount. Successful output is ordinary frozen04 journal metadata, with exact bigint amounts. No storage, posting, approval or financial authority API is added.

Source identifies each journal request, separately from Account owner, provider identity, MoneyEvent IDs and receipt/hash references. The same Account may use different explicitly declared sources across transactions. The context checks unauthenticated caller declarations for one call, without a durable/global Account-to-source registry or authorization. Wrapper/context are not persisted or universally enforced by existing SQL; provenance.source already belongs to the unchanged transaction header. Existing readers select ledger/account/currency rather than authenticated source. Raw evidence and financial truth remain external to this structural check.

The unchanged06 `account_normal_positive` reader computes expense **debit minus credit**. A controlled1250 debit fee/credit asset journal yields expense+1250. An explicit inverse yields zero; greater credits may yield negative totals. Exact per-line int64 wire limits and unbounded bigint aggregate arithmetic remain unchanged. No signed-money conversion, Number coercion, clamp, new balance API or fee policy is introduced.

A credit journal alone is not a linked reversal. The executable full reversal composition explicitly validates the original and new fee request, then calls unchanged09 `validateLedgerReversalCandidate` and, only inside owned disposable synthetic tests, `createLedgerReversalStore(...).append`. The original and inverse must have posted metadata, new transaction/entry IDs, same ledger/account/currency/positive amounts/multiplicity with every side swapped, and identical referenced snapshots. Original MoneyEvent IDs and receipt/contentHash references are retained; the reversal has its own explicit request source while the original source remains visible through the original link. Original records and posted status stay unchanged. Partial/drifted reversals refuse; an exact same-key retry returns the original linked receipt and a second key refuses. Pure13 validation alone does not establish reversal eligibility or override09 controls.
