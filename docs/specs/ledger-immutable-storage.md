# Immutable synthetic journal storage: M04.05

`packages/ledger` owns `createLedgerJournalStore(explicitConnectionUrl)`. Its `append(unknownJournalWire, unknownAccountCatalog)` revalidates the complete M04.04 candidate and supplied catalog before connecting. Invalid input returns frozen issues without a partial value or storage receipt. Valid input uses a private pooled connection for one parameterized autocommit call to `public.append_ledger_journal(jsonb,jsonb)`. `close()` releases the pool. No ambient database URL or shared caller transaction is accepted.

On acknowledged success the result is `{ ok: true, receipt: { contractVersion: "m04.05-ledger-storage.v1", transactionId, entryCount } }`, frozen and detached. The receipt acknowledges storage of supplied synthetic data; it does not change a header to posted, establish an accounting occurrence or grant authority. The full supplied header, clocks, status, source/event/receipt/hash references and retry key remain unchanged. Duplicate durable transaction or entry IDs reject, including identical input. Retry keys remain metadata: M04.08 owns key reservation and returning an original outcome.

## Durable encoding and references

The one migration stores public `ledger_transactions`, `ledger_account_snapshots` and `ledger_entries`, plus migration-tool metadata. Header JSONB uses the unchanged M04.02 wire contract. Journal and entry versions are stored explicitly. Entry amounts are canonical positive decimal strings at the SQL boundary and checked `bigint` columns, from1 through9223372036854775807. No money travels through Number. Database conservation uses exact `numeric` sums, so aggregate totals can exceed the per-line maximum.

Only accounts actually referenced by the journal are snapshotted. Snapshots are local to `(transactionId, accountId)`; no global Account registry or lifecycle is introduced. This does not establish account ownership or current membership. Composite foreign keys enforce transaction/ledger and transaction/account/ledger/currency consistency. No orphan or mismatched entry can be stored.

Account storage has its own explicit wrapper: `{ storageVersion: "m04.05-account-snapshot.v1", account: { ...M04.01Fields, name: { representation: "utf16_code_units", units: [...] } } }`. All other account fields are unchanged. Each `units` item is an integer0-65535 representing one original JavaScript UTF-16 code unit. The existing name length/control/surrounding-whitespace policy is checked on these units. This lossless encoding preserves astral characters and lone surrogates accepted by M04.01, which PostgreSQL JSONB cannot represent as ordinary strings. It does not amend the external Account contract. Readback decoding is currently integration-test-only; general lookup belongs to M04.07.

## Atomicity and immutable history

The append routine validates versioned JSON shape, header/provenance/clock metadata, encoded account snapshots, line amount encoding and references. It inserts a new header, referenced snapshots and entries, then checks nonempty per-currency debit/credit equality and absence of unused snapshots. A routine error aborts the whole statement, including rows inserted before the failure. Inserting an already committed transaction ID refuses before extending its history. An outer SQL transaction may still explicitly roll back a direct SQL call; the exported store owns its connection and returns only after its autocommit acknowledgement.

Separate pre-provisioned `causalledger_storage_owner` and `causalledger_storage_app` identities are required. The owner is a restricted non-superuser migration identity. The app is a distinct restricted identity without owner membership; it has only SELECT on the three storage tables and EXECUTE on the complete append routine. No direct INSERT/UPDATE/DELETE/TRUNCATE, object ownership, schema creation or trigger management is granted. Mutation triggers also refuse UPDATE/DELETE/TRUNCATE under the trusted owner, while privileged DDL administrators remain outside the application-role threat boundary. The down migration refuses populated history and only removes empty reviewed objects; operators must never use it against user databases.

The SECURITY DEFINER routine is owned by the restricted migration identity, uses qualified table/helper names and fixes `search_path` to `pg_catalog, pg_temp`. Default PUBLIC execution and helper execution are revoked; PUBLIC cannot create objects in the storage database's public schema. These controls follow the [PostgreSQL17 function security guidance](https://www.postgresql.org/docs/17/sql-createfunction.html). Roles are provisioned only by the explicit disposable test runner; production identity/tenant authorization and deployment are outside this slice.

## Failure and acknowledgement

`LedgerJournalStorageError` exposes `outcome` and a sanitized SQLSTATE, never raw database diagnostics. Failure to acquire a connection before issuing SQL is `not_stored`. A recognized server statement refusal (invalid data/range, constraints, SQL access/shape or immutable history) is `not_stored` because the autocommit statement rolls back. Connection loss, shutdown, internal errors or malformed acknowledgement after issuing SQL are `unknown`: the journal may already have committed. The store never retries automatically and never promises rollback merely because an acknowledgement was lost. Durable retry/recovery semantics remain M04.08.

## Acceptance and executable demonstration

The default ledger suite proves validation-before-I/O, exact wire encoding, immutable detached receipts and failure/acknowledgement handling with driver doubles. Doubles provide no PostgreSQL evidence. The valid synthetic USD1250 debit/credit demo receives one receipt; changing the credit to1249 refuses before connecting. The coordinator runs these tests; users do not need to run them before merge. Optional learning command in VS Code: `corepack pnpm --filter @causalledger/ledger test`.

`corepack pnpm test:ledger-storage` is the mandatory real PostgreSQL17 acceptance command. It requires explicit `LEDGER_STORAGE_TEST_ADMIN_URL` and `LEDGER_STORAGE_TEST_DISPOSABLE=YES_M04_05_SYNTHETIC_ONLY` from an owned isolated Compose environment. Missing configuration fails. It never falls back to `DATABASE_URL`, another database or mocks. Existing resources with its test names are refused. The runner verifies bootstrap database/version/loopback, creates its own named disposable database/roles, runs migration up/down/up, inspects exact public schema, runs SQL and store behavior tests, and verifies exact database/role identities again before removing only its owned resources. The existing CI job always cleans its Compose resources as a second boundary.

Acceptance covers complete durable independent readback; supplied metadata/status and Unicode preservation; exact maximum/large/cross-currency values; malformed/unbalanced/duplicate/range/reference refusal; no partial rows after a forced second-entry failure; explicit transaction rollback; app privilege and later-entry refusal; populated down-migration refusal; and reconnect preservation. Local Windows has no database tools, so local evidence is unit/type/control/workspace only. CI must execute these tests successfully on the final reviewed head before a storage guarantee or merge readiness is reported.

No account balance query, general transaction lookup, semantic retry, reversal, business category factory, event-to-posting mapper, raw evidence mutation, live money, production connection, agent financial-write/approval tool or exactly-once occurrence is implemented. Persistence of balanced caller-supplied synthetic data does not authenticate evidence or establish financial truth.
