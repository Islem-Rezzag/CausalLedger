# Customer liability account — M04.12

`m04.12-customer-liability-account.v1` is strict caller-supplied `{contractVersion,role:"customer_liability",account}`. It configures unchanged M04.01 Account metadata as liability/credit-normal, representing synthetic amounts owed to a declared customer/user/stored-balance holder. No name, provider or source-event reference determines owner or role; no new customer identity, defaults, normalization or generated ID.

`validateCustomerLiabilityAccountCandidate(unknown)` validates strict own enumerable data, delegates unchanged01 fields and requires the role owner's full-span canonical namespace/ID syntax. Namespace starts lowercase ASCII and has up to64 lowercase letters/digits/dot/hyphen; ID has1–128 ASCII alphanumeric-first characters followed by alphanumeric/dot/underscore/colon/hyphen. Trailing newlines reject, with a12-owned check. Detached frozen role/Account output or deterministic issues; closed metadata remains inspectable.

`validateCustomerLiabilityJournalCandidate(journal,configuration,context)` requires strict `{owner:{namespace,id},accounts}` context. Captured canonical owner must exactly equal the role Account.owner. A captured detached valid catalog must contain the complete exact role snapshot, active liability, configured ledger and one currency on all lines, configured liability participation and a distinct counteraccount. Full04 journal ID/reference/provenance/exact bigint arithmetic validation uses catalog.value. Every participating liability account must share this owner. Non-liability counters may have unrelated owners; unused other-owner catalog accounts are allowed. Output is an ordinary frozen04 journal with no storage/write/posting/approval method.

The unchanged06 reader uses `account_normal_positive`: liability balance is exact credit total minus debit total. A synthetic credit1250 liability/debit1250 asset produces liability balance+1250; debit250 reduces it to+1000; an explicitly supplied debit1000 offset reaches zero. Further debits may yield a negative balance, with no spending limit/floor/clamp or Number money. Raw debit-minus-credit movement is a different quantity and is not the reader's balanceMinorUnits. No new balance API or sign override is introduced.

Owner matching checks unauthenticated caller declarations within one call. There is no durable/global Account-to-customer registry or ownership authorization. Wrapper/context are not stored or universally enforced by SQL. The existing reader selects ledger/account/currency and category/normal side, not owner; two-owner durable examples use distinct explicit Account IDs in one ledger. Across separate calls this helper cannot establish immutable ownership. A balance or zero does not prove customer identity, real amounts owed, solvency, settlement, reconciliation, evidence authenticity or financial truth.

Unit/type and mandatory eighth owned PostgreSQL17 composition tests cover positive/debit-reduced/zero/negative/huge exact balances, both cutoffs, immutable readback, independent namespace/ID mismatches, participating other customers, canonical reference/descriptors/proxy capture, same-owner liability counters, unused foreign catalogs, wrong currency/ledger/snapshot/lifecycle/class/side/role/identities/provenance and pre-I/O refusal. All seven prior real suites (246 tests), THREE byte-identical migrations, empty UP/DOWN/UP, both populated upgrades, exact six public tables including pgmigrations/ten functions and owned/Compose cleanup remain required. No DDL, live customer balances, spending policy, owner authentication or agent financial authority. M04.13 and later remain unimplemented.
