# Synthetic payment authorization (M05.02)

`generatePaymentAuthorized(unknown)` creates a labelled synthetic provider occurrence and one declared delivery. It never contacts a provider, authorizes money, creates a canonical MoneyEvent, allocates durable evidence IDs, ingests receipts, stores evidence or posts ledger entries. Authorization is distinct from capture, payout and settlement; these later generators remain unimplemented.

## Request and versions

The exported readonly PaymentAuthorizedRequest has exactly20 required own enumerable data fields: schemaVersion, synthetic, scenarioId, observationCutoff, sourceId, sourceOccurrenceId, sourceRecordId, eventTime, deliveryId, receiptDescriptorId, observedAt, deliveryOrder, providerId, merchantId, payerId, paymentId, authorizationId, amountMinorUnits, currency, context. No default/trim/coercion or caller generatorVersion. Fixed versions: m05.02-payment-authorized-request.v1, m05.02-payment-authorized-record.v1 and m05.02-payment-authorized.v1. Generic manifest m05.01-simulator-manifest.v1 is unchanged.

Context has exactly sourceId/providerId/merchantId/payerId/paymentId/currency, each a string exactly matching its request declaration. This is per-call consistency, not an ownership lookup, authentication, registry or financial authorization check. Provider/merchant/payer/payment/authorization IDs use sim_provider_/sim_merchant_/sim_payer_/sim_payment_/sim_auth_ plus1–64 ASCII characters starting alphanumeric then alphanumeric/underscore/hyphen. Foundation metadata IDs retain their existing contracts. No durable rcpt_/evt_ ULIDs are allocated.

amountMinorUnits is a positive canonical decimal string1–128digits, first digit1–9. Zero-value verification, negative/decimal/exponent/leading-zero/numeric/BigInt inputs are unsupported. No Number conversion or signed64bit financial limit:128digits is an input resource policy. Currency is exactly3 uppercase ASCII letters and equals declared context currency. ZZZ is format-valid; no authoritative ISO4217 catalogue or currency minor-unit conversion is claimed.

Event time must be a supplied known canonical UTC string; generic manifests still permit null unchanged. Existing calendar0001–9999, whole-second/exact3millisecond Z precision rules apply. Observed time/cutoff/order retain unchanged validator rules. No host clock/randomness or chronology inference. Future declared deliveries remain in the full manifest even beyond cutoff; these are declarations, not actual received observations.

## Output and integrity

Success is a detached deeply frozen `{ok:true,value:SimulatorManifest,issues:[]}`. One provider source and one delivery retain caller source/occurrence/record/delivery/receipt identities. Compact JSON.stringify serialization has fixed key order, UTF8, no BOM/no newline. Raw keys: schemaVersion, synthetic:true, eventType:payment_authorized, sourceId, sourceOccurrenceId, providerId, paymentId, authorizationId, merchantId, payerId, amount:{minorUnits,currency,representation:integer_minor_units}, eventTime. SHA256 covers exactly those generated bytes. Descriptor/scenario/delivery/observed/order/cutoff metadata is excluded from raw occurrence bytes; changing it alone preserves bytes/hash. Economic deduplication/duplicate/delay/missing scenarios remain future work.

Own request and context data are captured once. Accessors/hidden/symbol/class objects fail; getters and unknown toJSON are never evaluated. Plain/null-prototype data accepted. Proxy trap side effects are not sandboxed, but unexpected traps fail invalid_object. Body primitives and consistency are checked before unchanged generic validation probes metadata with empty payload/hash; raw serialization sees only validated captured primitives. Final unchanged generic validation checks generated integrity/output.

## Stable errors

Failure is frozen `{ok:false,issues}` without value. Shape validation short-circuits by phase: root shape, context shape, body semantics, existing metadata. Unknown fields are lexical, then missing fields in exported request/context schema order. Invalid shape produces invalid_object at $ or $.context. Body order: schemaVersion, synthetic, role IDs in provider/merchant/payer/payment/authorization order, amountMinorUnits, currency, known eventTime type, then context fields in source/provider/merchant/payer/payment/currency order. Context nonstrings fail invalid_identity/invalid_currency; unequal strings fail invalid_reference. Metadata errors retain base ordering with $.sourceRecords[0].field and $.deliveries[0].field remapped to $.field. Duplicate mapped issues may remain; no partial output. Body semantic codes extend generic codes with invalid_amount/invalid_currency without changing generic validation.
